# 关卡制作规范

> 制作或修改任何关卡前必读。2026-10-16 可玩性改版后：关卡谜题由用户指定的强模型设计（D39），其他 AI 只按[关卡设计稿](#关卡设计稿)实现；所有关卡必须通过「校验」和「难度指标」两节的全部检查。

## 可玩性原则

首版九关的问题：每关只有一两个机关、状态不到 10 种、没有岔路和取舍，第 5～8 关甚至没有错觉连接。设计每一关时都要对照下面几条：

1. **一个「原来如此」**：每关都要有一个不显而易见的关键认识，例如「要站在桥上一起转」「先把桥转走，另一边才会接上」「光点在一条看似走不通的错觉路上」。写不出这一句话的关卡不合格。
2. **错觉是主角**：标准解法必须经过错觉连接（第 2 关起至少 1 处，第 3 章起至少 2 处）。不允许整关都是平地拼桥。
3. **取舍**：第 2 章起，标准解法中至少有一次操作在接上一处的同时断开另一处（求解器统计，见「难度指标」）。
4. **位置是资源**：第 2 章起，至少有一步必须先走到特定位置再操作，例如乘坐、压板。
5. **干扰路线**：第 3 关起，至少有一条看起来像通路、实际走不通或走了没用的路线。
6. **不能乱点通关**：第 2 章起，随机操作在限定步数内通关的概率要低于门槛。
7. **信息公开**：开局时所有路面、把手、光点都要能看见或推理出来，不靠隐藏信息为难玩家。
8. **往返有意义**：允许折返，但同一段路的机械性往返不超过 2 次。
9. **选做光点要更难**：第 2 章起的选做光点，应当要求比主线多理解一层机制，而不只是多走几格。

## 坐标系

- 积木坐标为整数格 `(x, y, z)`，`y` 向上。
- 相机从 `(+1, +1, +1)` 方向看向场景。屏幕上 `+x` 指向右下，`+z` 指向左下，`+y` 指向正上方。
- 每块积木只有三个面可见：顶面（`+y`）、右前面（`+x`，较暗）、左前面（`+z`，较亮）。
- 离相机越近，`x + y + z` 越大。

## 屏幕坐标

积木 `(x, y, z)` 的屏幕坐标为 `(a, b) = (x - y, z - y)`。

- 屏幕坐标相同的积木在画面上完全重合。
- 给定屏幕坐标 `(a, b)` 和高度 `y`，积木位置是 `(a + y, y, b + y)`。

**推荐的制作思路：先在屏幕坐标上画路线，再给每块路面选高度。** 屏幕上相邻、高度相同的是真实相邻；高度不同的就是错觉连接。

## 遮挡规则

两块屏幕相邻的路面 A、B，B 在 A 的屏幕下方（B 的 `a` 或 `b` 比 A 大 1）时：

> **B 的高度必须大于或等于 A 的高度。**

等价说法：屏幕上靠下的那块必须离相机更近或一样近，否则 A 的侧面会挡住 B 顶面的一角。反过来，B 在 A 的屏幕上方时，B 的高度必须小于或等于 A 的高度。

| A | B | 结论 |
| --- | --- | --- |
| `(2, 0, 0)`，屏幕 `(2, 0)`，高度 0 | `(7, 4, 4)`，屏幕 `(3, 0)`，高度 4 | B 在下方且更高，合格 |
| `(11, 4, 4)`，屏幕 `(7, 0)`，高度 4 | `(9, 1, 1)`，屏幕 `(8, 0)`，高度 1 | B 在下方但更低，不合格 |

## 关卡设计稿

关卡设计稿是设计者交给实现者的唯一依据，放在 `docs/levels/level-XX.md`（XX 为 01～14），必须包含：

1. **关名、章节、教学点**。
2. **「原来如此」**：一句话。
3. **屏幕草图**：用文字网格画出屏幕坐标，标注每格的高度、路面或结构、机关、光点、起点、终点。
4. **积木清单**：静态路面与结构积木的坐标和颜色、岛屿范围。
5. **机关清单**：类型、编号、中心或原点、积木偏移、档位或停靠位、把手位置、联动关系。
6. **光点清单**：位置，必需或选做。
7. **标准解法**：逐步列出，每步附一句为什么。
8. **干扰与陷阱**：玩家最可能走错的路线是什么，为什么走不通。
9. **预期指标**：最少步数、可达状态数、随机通关率、标准解法中的错觉连接数和取舍次数。

实现者把设计稿转成 `src/game/levels/level-XX.ts`，把预期指标写进 `src/game/levels/targets.ts`。实现时不得修改谜题本身；如果校验或指标不通过，停下来反馈，不要自己改布局或改目标。

## 关卡文件

- 每关一个文件：`src/game/levels/level-01.ts` 到 `level-14.ts`，在 `levels/index.ts` 中按顺序导出。
- 用 `levels/builders.ts` 的辅助函数搭积木，不要手写大段坐标数组。
- 数据结构见 [architecture.md](architecture.md#关卡数据)。

示例骨架（坐标仅作示意）：

```ts
import { defineLevel } from './builders'

export default defineLevel({
  id: 'level-05',
  title: '乘风',
  chapter: 2,
  hints: ['站在桥上转动，桥会带着你走'],
  build: (b) => {
    b.island({ x: [-1, 2], z: [-1, 3], y: -1 })
    b.path([0, 0, 2], 'terracotta')
    b.rotator({
      id: 'bridge',
      pivot: [3, 0, 2],
      blocks: [{ offset: [0, 0, -1] }, { offset: [0, 0, 1] }],
      handle: { block: [3, -1, 2], face: 'z' },
      links: [{ target: 'gate', reverse: true }],
    })
    b.orb({ tile: [6, 3, 3] })
    b.orb({ mechanism: 'bridge', block: 1, optional: true })
    b.start([0, 0, 2])
    b.goal([7, 3, 3])
  },
  solution: [
    { type: 'walk', to: [3, 0, 3] },
    { type: 'operate', mechanism: 'bridge' },
    { type: 'walk', to: [7, 3, 3] },
  ],
})
```

## 制作步骤

### 设计者（强模型）

1. 对照[设计稿的关卡表](design.md#章节与关卡)，写下教学点和「原来如此」。
2. 在屏幕坐标上画路线，选高度，检查每处错觉连接的遮挡规则。
3. 放机关、联动、光点，设计干扰路线和陷阱。
4. 用求解器验证：最少步数、可达状态数、随机通关率、取舍次数都落在目标范围内；标准解法就是最优解之一。
5. 写成关卡设计稿。

### 实现者

1. 按设计稿写关卡文件和目标。
2. 补结构：高处路面下加柱子、岛屿、底部岩层、装饰。
3. 跑 `npm test`，全部通过。
4. `npm run dev` 打开该关，开局、关键步骤、通关各截图一张，检查构图、错觉是否成立、装饰有没有挡住路。
5. 亲手按标准解法玩一遍，再试设计稿中的干扰路线，确认反馈正常。

## 构图

- 每关一个视觉主体（一座塔、一座桥、一组台阶），两到四座岛屿，留出足够的空白。
- 场景在屏幕坐标上的范围不超过 14 × 14，保证手机竖屏也能看清。
- 起点、终点和所有光点在开局时都能看见；如果光点在大型转盘背面，转盘转动后必须能看见。
- 路面顶板统一用浅色，结构积木按[美术方向](art-direction.md#配色)的用途选色，机关积木用青绿，把手用金色。
- 装饰物每关 3～6 个，只放在岛屿地面上，不放在任何路面的屏幕下方相邻处。

## 解法格式

```ts
type SolutionStep =
  | { type: 'walk'; to: Vec3 } // 走到「此刻」位于该坐标的路面
  | { type: 'operate'; mechanism: string } // 点击该机关的把手一次
```

- `walk.to` 是执行这一步时目标路面所在的世界坐标；机关上的路面按它当时的位置填写。
- 压板、光点不需要单独写步骤：停在压板上会触发，路过光点会收集。
- 标准解法必须收集全部必需光点，最后一步走到终点；步数必须等于求解器算出的最少步数。

## 难度指标

求解器（`core/solver.ts`）在规则层上穷举状态，计算以下指标：

| 指标 | 定义 |
| --- | --- |
| 最少步数 | 从开局到通关（集齐必需光点）的最少动作数。一次行走（到任意可达路面）或一次机关操作各算 1 个动作 |
| 全收集最少步数 | 集齐全部光点（含选做）并通关的最少动作数 |
| 可达状态数 | 从开局出发能到达的不同状态数。状态 = 小人位置 + 各机关档位或停靠位（含往返方向）+ 已收集光点 + 已用压板 |
| 死局状态数 | 可达但再也无法通关的状态数（由一次性压板等不可逆操作造成） |
| 随机通关率 | 随机代理每步在全部合法动作中均匀随机选一个，在 N 步内通关的比例；固定随机种子，跑 500 次 |
| 错觉连接数 | 标准解法的行走路线中，跨越「屏幕相邻但三维不相邻」的次数 |
| 取舍次数 | 标准解法中，操作后小人可达的路面集合既有新增又有减少的操作次数 |

### 门槛

每关的具体目标写在 `levels/targets.ts`，由设计者给出，必须落在本章的范围内：

| 章 | 最少步数 | 可达状态数 | 随机通关率 | 错觉连接数 | 取舍次数 |
| --- | --- | --- | --- | --- | --- |
| 一 | 2～6 | 不要求 | 不要求 | 第 1 关 ≥ 0，其余 ≥ 1 | 不要求 |
| 二 | 4～12 | ≥ 16 | 30 步内 ≤ 60% | ≥ 1 | ≥ 1 |
| 三 | 7～16 | ≥ 40 | 40 步内 ≤ 35% | ≥ 2 | ≥ 1 |
| 四 | 12～24 | ≥ 80 | 60 步内 ≤ 20% | ≥ 2 | ≥ 2 |

第 2～4 章的第一关可以比本章最少步数下限低 2 步，用于引入新机制。

## 校验

`levels/levels.test.ts` 对每个关卡执行以下检查，全部通过才算合格：

1. **基本结构**：关卡编号唯一；起点、终点都是路面；终点不在机关上；机关编号唯一；压板、联动、光点引用的机关和积木都存在；联动不能指向自己。
2. **无重叠**：在每个机关的每个档位或停靠位组合下，没有两块积木占用同一格。组合数超过 64 时，只检查求解器的全部可达状态。
3. **乘坐安全**：所有可达状态中，小人所在格子的上方都没有积木。
4. **解法可行**：用模拟器从开局逐步执行标准解法，每一步都成功，最后一步结束时通关。
5. **可见性**：执行解法时，每次行走经过的路面在行走开始时顶面可见（顶面 5 点采样，沿 `(1, 1, 1)` 发射射线，不碰到其他积木）。
6. **遮挡规则**：解法中每次跨越错觉连接都满足遮挡规则。
7. **把手与光点可见**：把手所在侧面中心、开局时每个光点所在路面的顶面中心，沿 `(1, 1, 1)` 不被挡住。
8. **构图范围**：所有积木在所有可达状态下的屏幕坐标范围不超过 14 × 14。
9. **难度指标**：求解器算出的各项指标落在 `targets.ts` 的目标内；标准解法步数等于最少步数。

## 常见错误

- 错觉连接往屏幕下方走时高度降低，违反遮挡规则。
- 整关都在同一高度，只是在平地上拼桥（首版第 5～8 关的问题）。
- 只有一个机关、一种用法，玩家点一下就通。
- 每个操作都只带来好处，没有取舍。
- 乘坐后小人头顶撞到积木。
- 一次性压板造成的死局没有在设计稿中说明（死局可以存在，但必须是有意设计的陷阱）。
- 为了让测试通过而修改 `targets.ts` 或删减谜题。
